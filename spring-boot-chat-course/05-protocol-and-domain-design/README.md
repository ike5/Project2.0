# Module 05 — Protocol & Domain Design

**Goal:** Design the message envelope, identity, and acknowledgement scheme that
every later module depends on — because protocol mistakes are the ones you can't
refactor away once clients are in the wild.

⏱️ ~5 hours · **Prerequisites:** Modules 00–04.

---

## Why this module comes before scaling

You can rewrite your fan-out layer on a Tuesday. You cannot rewrite your wire
protocol, because a million installed clients speak the old one and will keep
speaking it for years.

Three decisions made here determine whether Modules 09–13 are straightforward or
impossible:

1. **Does the client generate an ID before sending?** If not, you cannot dedup,
   which means you cannot safely retry, which means you cannot have
   at-least-once delivery.
2. **Is there a per-room sequence number?** If not, a client can never *know* it
   missed a message — only notice, eventually, by comparing with a friend.
3. **Is there a version field?** If not, your first protocol change is a flag day.

Get these three right and the rest of the course is mechanical. Get them wrong
and Module 10 has nowhere to stand.

## The two-ID rule

Every message has **two** identities, and conflating them is the most common
protocol bug in chat.

```json
{
  "clientId": "01H8XGJQ4V2K9NPZ0Y3RTBWMDC",   ← generated by the CLIENT, before sending
  "id":       "7241938472948572160",           ← assigned by the SERVER, on persist
  "seq":      48213                            ← position in this room's stream
}
```

| ID | Generated by | Purpose | Lifetime |
|----|-------------|---------|----------|
| `clientId` | Client, before the first send attempt | **Idempotency.** The server recognizes a retry and returns the original result instead of creating a duplicate. | Until the dedup window expires |
| `id` | Server, at persist time | Canonical identity for edits, deletes, replies, reactions | Forever |
| `seq` | Server, per room, monotonic | **Gap detection and resume.** | Forever |

### Why the client must generate an ID

```
Client sends message ──▶ Server persists ──▶ ACK ──✗ (network dies here)
Client times out, retries ──▶ Server persists AGAIN ──▶ duplicate
```

The network failed *after* the server did the work. The client cannot tell this
apart from "the server never got it." Its only safe options are:

- **Retry** — and risk a duplicate, unless the server can recognize the retry.
- **Don't retry** — and risk losing a message the user thinks they sent.

Both are bad. `clientId` makes retry safe:

```sql
INSERT INTO messages (id, room_id, client_id, ...) VALUES (...)
ON CONFLICT (room_id, client_id) DO NOTHING
RETURNING id, seq;
```

If nothing is returned, it was a retry — look up and return the original.
**The retry is now free**, and the client can retry as aggressively as it likes.

> **This is what "exactly-once" actually means in practice.** Nobody achieves
> exactly-once *delivery*; the network won't allow it. What systems deliver is
> at-least-once delivery plus **idempotent processing**, which is observationally
> identical and is achievable. `clientId` is the whole trick.

Use a **UUIDv7 or ULID**, not UUIDv4: they're time-sortable, so the dedup index
stays dense and you can range-delete expired keys instead of scanning.

### Why sequence numbers, and why per-room

Message IDs are globally unique but say nothing about *completeness*. A client
holding messages `...7241938472948572160` and `...7241938472948572400` has no
idea whether something sits between them.

```
seq: 48211  48212  48213  ██████  48215
                            ↑
              the client KNOWS it's missing 48214
```

Per-room, not global, because:
- A global sequence is a single point of contention (Module 14 kills it entirely
  when you shard).
- A client only cares about the rooms it's in. A global gap is meaningless to it.
- Per-room sequences let each room's stream be resumed independently.

The `seq` is the **resume cursor**. Module 10 builds `RESUME room.7 from 48213`
on top of it.

## The envelope

Every frame — message, typing indicator, receipt, control — shares a shape:

```json
{
  "v":    1,
  "type": "message.create",
  "ts":   1735689600123,
  "room": "7",
  "data": { }
}
```

| Field | Why |
|-------|-----|
| `v` | Protocol version. Costs one byte; buys you the ability to change anything later. |
| `type` | Namespaced verb (`message.create`, `presence.update`, `typing.start`). Lets one socket carry every kind of traffic and lets a client route on a single switch. |
| `ts` | Server time at emission. Used for latency measurement and for ordering display when `seq` isn't applicable. |
| `room` | Routing key. Redundant with the STOMP destination, and deliberately so — see below. |
| `data` | Type-specific payload. |

### Why `room` is duplicated in the payload

The STOMP destination already says `/topic/room.7`. Repeating it costs ~12 bytes.
Worth it because:

- **Transport independence.** In Module 09 these envelopes flow through Redis
  Streams, which have no STOMP destination. Self-describing payloads survive the
  transport change.
- **Logging and debugging.** A message in a log or a stream is interpretable on
  its own.
- **Client-side routing.** A client multiplexing several rooms over one
  subscription doesn't have to thread the destination through its callback.

> **The principle: make payloads self-describing.** Any field you can only
> reconstruct from transport metadata becomes a bug the moment you change
> transports — and you will change transports, twice, in this course.

### Naming: `messageId` vs `i`

At 50 bytes of body, JSON field names can be 40% of the frame:

```json
{"v":1,"type":"message.create","ts":1735689600123,"room":"7","data":{"clientId":"01H8XG...","body":"ok"}}
```
That's 104 bytes for a 2-byte message.

Options, in increasing order of severity:

| Approach | Saving | Cost |
|----------|--------|------|
| Verbose JSON | — | Readable in every tool |
| Short keys (`{"v":1,"t":"m.c","d":{...}}`) | ~30% | Unreadable; needs a mapping doc |
| MessagePack / CBOR | ~40% | Binary; DevTools shows garbage |
| Protobuf / FlatBuffers | ~60% | Schema registry, codegen, versioning discipline |

**Pulse keeps verbose JSON.** The reasoning is worth stating because it's the
kind of judgment this course is about: at Pulse's target scale the bandwidth is
not the constraint (Module 04 showed CPU and outbound queue depth are), and
readable frames in DevTools are worth real money in debugging time. **Revisit if
mobile data cost becomes a product concern** — which is exactly when Discord and
Slack switched to binary encodings, and not before.

## The acknowledgement ladder

"Delivered" is not one thing. Chat UIs show four distinct states, and each needs
a different signal:

```
   ┌─────────┐  send   ┌──────────┐  server   ┌───────────┐  recipient  ┌──────┐
   │ pending │────────▶│  queued  │──────────▶│ delivered │────────────▶│ read │
   │  (grey) │         │  (✓)     │           │   (✓✓)    │             │(blue)│
   └─────────┘         └──────────┘           └───────────┘             └──────┘
   optimistic          server ACK              per-recipient            explicit
   local render        (persisted)             delivery receipt         read receipt
```

| State | Signal | Who sends it | Cost |
|-------|--------|-------------|------|
| **pending** | none — render optimistically | client itself | free |
| **queued** | server ACK with `id` + `seq` | server → sender | 1 frame per message |
| **delivered** | delivery receipt | each recipient → server → sender | **N frames per message** |
| **read** | read receipt | recipient (debounced) → server → sender | ~1 frame per read burst |

⚠️ **The "delivered" row is a scaling trap.** Per-recipient delivery receipts
invert your fan-out: a message to 500 people produces 500 receipts back to one
sender. That's a 500× amplification pointed at a single connection.

How real systems handle it:
- **1:1 DMs** — full delivery receipts. N=1, so it's free.
- **Small groups** — delivery receipts, sometimes aggregated ("3 of 5").
- **Large rooms** — **no delivery receipts at all.** Slack does not tell you who
  received your `#general` message, and that's an architecture decision, not an
  oversight.

Pulse: ACK always; delivery receipts only for rooms under a configurable
threshold; read receipts always, but **debounced client-side** to at most one per
2 seconds per room.

### Optimistic send and reconciliation

```
1. User hits enter
2. Client renders immediately with clientId, state=pending
3. Client sends
4. Server ACKs with {clientId, id, seq}
5. Client MATCHES ON clientId, upgrades the existing bubble to state=queued
6. The broadcast arrives with the same clientId — client sees it's already
   rendered and does NOT add a second bubble
```

Step 6 is why `clientId` must be **echoed in the broadcast**, not just the ACK.
Without it, the sender sees their own message twice: once optimistically, once
from the fan-out. Every chat client has had this bug.

## Ordering: what you can and cannot promise

**You can promise:** messages within one room are delivered in `seq` order to
every client, and a client can detect gaps.

**You cannot promise:** that `seq` order matches the order users *pressed enter*.
Two people in different cities pressing enter "at the same time" have no
meaningful global order — the server assigns one, and it's arbitrary. This isn't
a limitation to fix; it's special relativity with worse latency.

**Practical consequences:**

- Sort the UI by `seq`, never by client timestamp. Client clocks are wrong,
  sometimes by hours, sometimes deliberately.
- Show the *server's* `ts` as the displayed time.
- When an optimistic message gets a `seq` lower than one already rendered, **it
  must move**. Clients that append-only will show messages out of order after a
  slow send. Design for it.
- Threads/replies reference a parent `id`, which sidesteps ordering entirely for
  the cases users care most about.

## Schema evolution

The rules that keep `v:1` clients working forever:

| Change | Safe? | Why |
|--------|-------|-----|
| Add an optional field | ✅ | Old clients ignore unknown fields (configure your parser to!) |
| Add a new `type` | ✅ | Old clients ignore unknown types — **if you told them to** |
| Make an optional field required | ❌ | Old clients don't send it |
| Remove a field | ❌ | Old clients read it |
| Change a field's type | ❌ | Silent corruption; the worst kind |
| Rename a field | ❌ | It's a remove plus an add |
| Change the meaning of a value | ❌❌ | The most dangerous, because nothing detects it |

```java
@JsonIgnoreProperties(ignoreUnknown = true)     // the single most important annotation
public record Envelope(int v, String type, long ts, String room, JsonNode data) {}
```

And on the client:
```js
switch (env.type) {
  case 'message.create': return renderMessage(env.data);
  case 'typing.start':   return showTyping(env.data);
  default:               return;          // forward compatibility, deliberately
}
```

That `default:` is a protocol decision. Without it, shipping a new message type
breaks every old client.

**When you genuinely must break compatibility:** bump `v`, support both for a
deprecation window, and have the server negotiate at CONNECT time
(`accept-version`-style). Pulse's `CONNECT` carries a client version and the
server records it — so you can measure how many old clients remain *before*
deciding to drop support. Deprecation without telemetry is guessing.

## The Pulse protocol, specified

```
message.create   client→server   { clientId, body, replyTo? }
message.ack      server→client   { clientId, id, seq, ts }
message.new      server→client   { id, clientId, seq, room, sender, body, ts, replyTo? }
message.edit     client→server   { id, body }
message.delete   client→server   { id }

typing.start     client→server   { }                        (rate limited, at-most-once)
typing.update    server→client   { room, users: [...] }     (aggregated, debounced)

read.upto        client→server   { seq }                    (debounced 2s)
read.update      server→client   { room, user, seq }

resume           client→server   { room, fromSeq }          (Module 10)
resume.batch     server→client   { room, messages: [...], hasMore }

control          server→client   { action, reason, retryAfterMs? }
error            server→client   { code, message, clientId? }
```

Two things to notice:

- **`typing.*` is deliberately at-most-once and aggregated.** It's the traffic
  with the highest volume and the lowest value. Module 07 sends it over Pub/Sub
  while messages go over Streams — different semantics for different traffic is a
  design decision, not an inconsistency.
- **`control` exists from day one.** It's how the server says "I'm draining,
  reconnect in 3,400 ms with jitter" (Module 18) or "your token expired,
  re-auth" (Module 21). Retrofitting a control channel later is painful.
