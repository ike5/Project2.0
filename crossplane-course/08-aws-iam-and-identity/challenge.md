# Challenge 08 — Identity You'd Defend in an Audit

Solutions in [`solutions/`](./solutions/). Try first.

## Tasks

1. **Add a permissions boundary to the platform API.** `XAppIdentity` currently
   creates roles with no boundary, so a developer who can create an `XAppIdentity`
   can create a role with any permissions the composition will write. Add a
   permissions boundary that caps every generated role, and write the boundary policy
   itself.

   Then answer: what specifically could a developer do today, before your change,
   that they cannot do after it?

2. **Support cross-account provisioning.** Extend the platform so an `XAppIdentity`
   can target a *different* AWS account. The composition should select a
   `ProviderConfig` based on a `spec.account` field (`dev`, `staging`, `prod`).
   Write the `assumeRoleChain` configs and explain what stops a developer in the
   `dev` namespace from targeting the `prod` account.

3. **Find the escalation path.** Here's a policy a colleague wants to ship:
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [{
       "Effect": "Allow",
       "Action": ["iam:PassRole", "ec2:RunInstances"],
       "Resource": "*"
     }]
   }
   ```
   They argue it's fine because it grants no data access. **They are wrong.** Explain
   the exact escalation path, then write a corrected version that lets them launch
   instances without it.

4. **Migrate off IAM users.** Module 06's challenge created an IAM user and access key
   per app. Rewrite that composition to use IRSA instead: an IAM role, a trust policy
   pinned to the app's ServiceAccount, and an annotated ServiceAccount — with no
   access key anywhere.

   Then describe the migration for an app that's already running with a static key:
   what order do you do things in so there's no downtime, and how do you verify the
   old key is genuinely unused before deleting it?

5. **Stretch — policy tests in CI.** Write a script that extracts every IAM policy
   document from your compositions (via `crossplane render`), validates each as JSON,
   and fails on: `"Action": "*"`, `"Resource": "*"` combined with a non-`Deny` effect,
   and `s3:ListBucket` paired with a `/*` resource ARN. Make it exit non-zero so CI
   fails.

## Success criteria
- [ ] Every role generated by `XAppIdentity` carries a permissions boundary, and you
      named a concrete capability the boundary removes.
- [ ] Cross-account targeting works via `ProviderConfig` selection, and you explained
      the control preventing a dev namespace targeting prod.
- [ ] You explained the `iam:PassRole` + `ec2:RunInstances` escalation path precisely
      and wrote a safe alternative.
- [ ] The Module 06 composition uses IRSA with no access key, and you wrote a
      no-downtime migration order including how to verify the old key is unused.
- [ ] You can state the difference between a trust policy and a permission policy
      without looking it up.
