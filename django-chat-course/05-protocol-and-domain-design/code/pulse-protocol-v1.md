# Pulse Wire Protocol — v1 (normative)

The contract between a Pulse client and a Pulse server over a single WebSocket
connection. Later modules link here rather than restating it; if a module's code
disagrees with this file, this file is wrong and should be updated in the same
change.

- **Transport:** WebSocket (RFC 6455), text frames, UTF-8 JSON.
- **Subprotocol:** the client SHOULD offer `pulse.v1` in `Sec-WebSocket-Protocol`.
  A server that speaks v1 echoes it. A server that does not echo any subprotocol
  is pre-v1 (Module 04) and MUST be treated as v1-compatible.
- **URL:** `/ws/room/<slug>/`. One socket per room in v1; Module 17 multiplexes
  many rooms over one socket, which is why `room` appears in every envelope.
- **Authentication:** a single-use ticket in the query string
  (`?ticket=<opaque>`), minted by `POST /api/ws-ticket/`. Modules 04–20 also
  accept the DEBUG-only `?as=<username>` shim; it MUST NOT be enabled outside
  development.

---

## 1. The envelope

Every frame in both directions:

```json
{ "v": 1, "type": "<namespaced.verb>", "room": "room.<slug>",
  "ts": 1735689600123, "data": { } }
```

| Field | Type | Direction | Notes |
|-------|------|-----------|-------|
| `v` | int | both | Protocol major version. Absent means 1. |
| `type` | string | both | See §3. Unknown types MUST be ignored by clients. |
| `room` | string | both | `room.<slug>`. Equal to `chat_message.room_id` in the store. |
| `ts` | int | both | Epoch **milliseconds**, **server clock**. Clients MUST NOT use their own clock for display or ordering. |
| `data` | object | both | Type-specific. Unknown keys MUST be ignored by clients. |

**Compatibility rules.**

- Clients MUST ignore unknown `type` values (a `default:` branch that returns).
- Clients MUST ignore unknown keys inside `data`.
- Servers MUST reject unknown client→server types and unexpected `data` keys with
  an `error` frame (§4). The asymmetry is deliberate: strict about what you accept
  from a client you do not control, liberal about what you accept from a server
  you do.
- Adding an optional `data` key, or a new `type`, is a **compatible** change.
  Removing a key, renaming one, changing a type, or changing the *meaning* of a
  value is **incompatible** and requires a `v` bump.

## 2. Identity

Three identifiers, never interchangeable:

| Field | Generated by | Format | Purpose |
|-------|-------------|--------|---------|
| `client_id` | Client, before the first send attempt | ULID / UUIDv7, 10–64 chars | Idempotency key. Unique per `(room, client_id)`. |
| `id` | Server, at persist time | int64 (Module 12: Snowflake) | Canonical identity for edits, deletes, replies, reactions. |
| `seq` | Server, per room, **gapless**, monotonic | int64 | Ordering, gap detection, resume cursor. |

A client MUST reuse the same `client_id` for every retry of the same message. A
server MUST return the original `id`, `seq` and `ts` for a retry and MUST NOT
re-broadcast it.

`seq` is gapless within a room. A client observing `seq != last_seq + 1` MUST
treat the intervening values as missing and MAY issue a `resume` (§3.5).

## 3. Message types

### 3.1 Messages

| Type | Direction | `data` |
|------|-----------|--------|
| `message.create` | C→S | `client_id` (req), `body` (req, 1–4096 chars after strip), `reply_to` (opt, int) |
| `message.ack` | S→C | `client_id`, `id`, `seq`, `duplicate` (bool) |
| `message.new` | S→C | `id`, `seq`, `client_id`, `sender`, `body`, `reply_to` |
| `message.edit` | C→S | `id` (req), `body` (req) |
| `message.update` | S→C | `id`, `seq`, `body`, `edited_at` |
| `message.delete` | C→S | `id` (req) |
| `message.removed` | S→C | `id`, `seq` |

`message.ack` goes only to the sender. `message.new` goes to every member of the
room **including the sender** — which is why `client_id` is echoed: the sender
uses it to recognize its own optimistic bubble instead of rendering a second one.

`message.ack` and `message.new` are independent frames and MAY arrive in either
order. Clients MUST key reconciliation on `client_id`, not on arrival order.

### 3.2 Presence and typing

| Type | Direction | `data` |
|------|-----------|--------|
| `presence.update` | S→C | `user`, `state` (`join`\|`leave`), `online` (array) |
| `typing.start` | C→S | — (rate limited to 1 per 3 s per room, at-most-once) |
| `typing.update` | S→C | `users` (array, aggregated, at most 1 frame per room per second) |

Typing traffic is explicitly **at-most-once and lossy**. It MUST NOT be given
durable delivery; Module 09 routes it over Pub/Sub while messages go over
Streams.

### 3.3 Read state

| Type | Direction | `data` |
|------|-----------|--------|
| `read.upto` | C→S | `seq` (req) — debounced client-side to at most 1 per 2 s per room |
| `read.update` | S→C | `user`, `seq` |

Read state is a **high-water mark**, not a per-message receipt. Per-recipient
*delivery* receipts are emitted only for rooms with at most
`PULSE_RECEIPT_MAX_MEMBERS` (default **16**) members, because they invert
fan-out: N recipients produce N frames aimed at one socket.

### 3.4 Heartbeat

| Type | Direction | `data` |
|------|-----------|--------|
| `ping` | C→S | `ts` (client clock, echoed back) |
| `pong` | S→C | `ts` (the client's value), `server_ts` |

Interval: **10 seconds**, client-driven, inside a normal data frame. This is
independent of, and in addition to, WebSocket control-frame pings
(`--ws-ping-interval`), because some proxies strip control frames. The `ts` echo
gives the client a free RTT sample.

### 3.5 Resume (Module 10)

| Type | Direction | `data` |
|------|-----------|--------|
| `resume` | C→S | `from_seq` (req) — "I have everything up to and including this" |
| `resume.batch` | S→C | `messages` (array of `message.new` `data` objects), `from_seq`, `to_seq`, `has_more` |

A client MUST issue `resume` after any reconnect and after any detected gap.
A server MUST return messages in ascending `seq` order and MUST set `has_more`
when it truncated the batch.

### 3.6 Control

| Type | Direction | `data` |
|------|-----------|--------|
| `control` | S→C | `action`, `reason` (opt), `retry_after_ms` (opt) |

Defined actions: `drain` (Module 18 — reconnect after `retry_after_ms` with full
jitter), `reauth` (Module 21 — present a fresh ticket in-band), `revoked`
(membership removed), `rate_limited` (Module 11).

## 4. Errors

```json
{"v":1,"type":"error","room":"room.7","ts":1735689600123,
 "data":{"code":"body_too_long","message":"body exceeds 4096 chars",
         "max":4096,"got":5000,"client_id":"01JQ…"}}
```

`code` is stable and machine-readable; `message` is for humans and MAY change.
`client_id` is present whenever the offending frame carried one, so a client with
several messages in flight can mark the right bubble failed.

| `code` | Meaning | Client action |
|--------|---------|---------------|
| `bad_frame` | Not a JSON object, or `data` is not an object | Bug. Log, do not retry. |
| `unknown_type` | Server does not implement this type | Bug or version skew. Do not retry. |
| `unsupported_version` | `v` exceeds the server's | Downgrade to `server_version` or prompt to update. |
| `unexpected_fields` | Fields outside the allowlist | Bug. Do not retry. |
| `missing_fields` | Required fields absent | Bug. Do not retry. |
| `empty_body` / `body_too_long` / `bad_client_id` | Validation | Surface to the user; do not retry unchanged. |
| `rate_limited` | Too fast (Module 11) | Back off by `retry_after_ms`, then retry with the **same** `client_id`. |
| `not_a_member` | Authorization lost mid-connection | Stop sending; the socket will close with `4403`. |

**An `error` frame MUST NOT close the connection.** Conditions the connection
cannot continue past use close codes instead:

| Close code | Meaning |
|-----------|---------|
| `1009` | Frame exceeded the transport limit (`--ws-max-size`) |
| `4008` | Slow consumer; the server chose to drop you rather than degrade the room |
| `4009` | Application-level frame too large |
| `4401` | Unauthenticated — sent **before** the handshake completes |
| `4403` | Authenticated but not authorized for this room |
| `4429` | Sustained abuse (Module 21) |

Codes `4000–4999` are application-defined per RFC 6455. Distinguishing them from
`1006` (abnormal close, no frame received) is what lets a client tell "get a new
credential" apart from "the network died, just reconnect".

## 5. Reserved for internal use

These are **channel-layer event types**, not wire types. They never appear on a
socket and a client sending one MUST receive `unknown_type`:

```
chat.message   chat.revoke   chat.overflow   chat.control   worker.beat
```

Wire types are namespaced `message.*`, `presence.*`, `typing.*`, `read.*`,
`resume*`, `control`, `error`, `ping`, `pong`. Internal event types are
namespaced `chat.*`. Keeping the namespaces disjoint means an internal refactor
is never a protocol break.
